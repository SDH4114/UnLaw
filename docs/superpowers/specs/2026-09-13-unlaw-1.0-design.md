# Unlaw 1.0 design

## Product direction

Unlaw 1.0 keeps one extension contract: a command is a directory containing `main.py`. The core gains user-facing configuration and diagnostics, but no registry, daemon, shell evaluator, AI layer, or plugin framework. Runtime code remains Python 3.11+ standard-library-only.

## First-run layout

Every CLI invocation calls an idempotent bootstrap that creates `${XDG_CONFIG_HOME:-~/.config}/unlaw`, `commands`, and `templates/{commands,python,rust,cpp}`. It creates `config.toml` only when absent and never overwrites commands or templates. Writes to configuration use a temporary file and `os.replace`.

The generated configuration contains `core`, `aliases`, `git`, `projects.python`, `projects.rust`, `projects.cpp`, and `mac` sections. Defaults preserve V1 behavior. Unknown keys are retained when configuration is rewritten; invalid known values produce a concise error rather than a traceback.

## CLI and configuration UX

Global flags are `--verbose`, `--dry-run`, `--no-color`, and `--version`. Aliases are arrays of tokens, expand before dispatch, append user arguments, and reject cycles. `ul commands` supports concise, verbose, and JSON output; `ul which` reports the exact script and whether it is user or built-in. Unknown commands suggest close matches.

`ul config path|show|get|set|edit|check|reset` manages configuration. `set` accepts TOML scalar/array syntax and dotted keys; bare text becomes a string. `reset` requires `--yes` and creates a timestamped backup. `edit` respects `$VISUAL`, then `$EDITOR`, then `open -t` on macOS. `ul completion zsh` prints a completion function based on `ul commands`.

## Execution and safety

Commands continue to run as `[sys.executable, main.py, *args]`; no path uses `shell=True`. Dry-run prints the resolved invocation without executing it. Verbose mode prints source and timing. A configured timeout maps to exit code 124. User commands override built-ins. System command names remain reserved.

## Built-in commands

`git` keeps the no-argument add/commit/push workflow and adds `status`, `pull`, `push`, `commit`, and `sync`. It stops on the first failure and reads `git.auto_push`.

`py` supports `--uv`, `--venv`, `--no-venv`, and `--git`; `auto` prefers uv when installed and otherwise uses `venv`. `rust` delegates to Cargo and supports `--bin`, `--lib`, and `--git`. `cpp` creates a CMake project with configurable C++ standard and optional Git initialization. Existing destinations are never overwritten.

Each generator applies files from its user template directory when present. Text placeholders `{{project_name}}` and `{{cpp_standard}}` are replaced; binary files are copied unchanged. The command template remains customizable at `templates/commands/main.py`.

`doctor` supports human, verbose, and JSON output; checks layout, config validity, Python, uv, Git, Cargo, CMake, Harness, Harness permissions, LM Studio, and future Voice availability. It never requests macOS permissions. `ul init` re-runs bootstrap and reports paths.

## Testing and packaging

Tests use temporary XDG directories and current-directory sandboxes. They cover bootstrap idempotence, atomic config round-trips, aliases, dry-run, command metadata, generator modes, Git workflows, doctor JSON, completion output, timeouts, and V1 regressions. A clean wheel is installed into a temporary venv and both entry points plus real project generators are smoke-tested.
